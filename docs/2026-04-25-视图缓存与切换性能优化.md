# 2026-04-25 视图缓存与切换性能优化

紧接 2026-04-24 的引用 / 媒体渲染重构之后，本次专门解决"切换视图卡顿"
和"引用源文件改动后什么时候应该重渲"两个体验问题。

## 一、问题与目标

### 1.1 卡顿症状

每次点击大纲 / 思维导图 / 文档 / 表格 / 演示 这些 tab 都会经历：

1. `syncAll()` —— 当前视图全树 `querySelectorAll('[data-path][data-field]')`，
   每个节点都做一遍 `mergeEditableTextAndMedia`；
2. `renderCurrentView()` —— 即使数据一字未改，也整树重新构建 DOM；
3. `_resolveAsyncRefs()` —— 跑一次 `querySelectorAll('[data-ref-async]')`；
4. `_ensureEmbeddedMediaLoaded()` —— 全文档 `JSON.stringify` 然后 `.includes('udd.ref-docs.')`
   去判断要不要懒加载——文档大时开销很可观。

也就是说，"什么都没改但切回来一次" 也会触发四遍全树扫描，只是为了从 0 重建一份
跟之前一模一样的 DOM。

### 1.2 引用更新的语义需求

用户发问："引用的源文件如果改动了，是不是看不到更新？"

要求：

- **默认不做**自动版本判定（避免维护"什么算一次实质性改动"的判定规则
  在未来跟新功能耦合带来 bug）；
- 提供一个**手动刷新**入口，用户主动点 → 强制重渲 + 重新读取所有引用 / 媒体；
- 真的对数据 / 渲染语义产生影响的若干"必要触发点"自动失效缓存。

## 二、整体方案

### 2.1 缓存模型

每个视图实例上挂两个标记位：

| 标记 | 含义 |
|---|---|
| `_rendered` | 该视图当前 DOM 是否已经按最新 data 完整渲染过 |
| `_inputDirty` | `_rendered=true` 之后，contentEditable 是否真的发生过 input 事件 |

切换视图（`switchView`）时：

1. 当前视图先调一次 `syncAll()` 把 contentEditable 文本回写到 `data`
   （`_inputDirty=false` 时直接 `return`，跳过整树扫）；
2. 切到目标视图，若 `target._rendered === true` ⇒ **跳过 `render`**，仅做轻量补齐：
   - outline / document：再跑一次 `_resolveAsyncRefs`（异步引用占位元素一般已经
     被 ref 解析覆盖，再跑一次也是极少量的 DOM 节点）；
   - 其它视图：什么都不做；
3. 否则正常 `render`，render 末尾标记 `_rendered=true`。

### 2.2 失效策略

**缓存只在数据 / 渲染语义真的变了时清掉**，分两档：

| 触发点 | 范围 | 调用 |
|---|---|---|
| `markDirty()`（用户敲字 / 撤销 / 改样式 / 插媒体 / 插表格 / 折叠 等所有数据变更最终都走它） | 其它视图 | `_invalidateOtherViews()` |
| `toggleRenderMode()` `toggleContentSource()` | 全部视图 | `_invalidateAllViews()` |
| `switchSession()` `closeSession()` `_addSessionAndSwitch()` | 全部视图 | `_invalidateAllViews()` |
| 用户点「🔄 刷新」按钮 | 当前视图（强制重渲） | `refreshCurrentView()` |

> 之所以 `markDirty` 只清 *其它* 视图：当前视图是用户正在操作的，DOM 已经
> 通过 contentEditable 实时更新或马上要 `renderCurrentView`，没必要再清。
> 其它视图却必须在下次切过去时拿最新数据重渲。

### 2.3 手动刷新

UI 在「渲染 on/off」旁加了一个「🔄 刷新」按钮，绑定 `refreshCurrentView`：

```js
refreshCurrentView() {
  this._getViewByName(this.currentView)._rendered = false;
  this.renderCurrentView();
  toast('已刷新');
}
```

什么时候点：

- 引用的另一个 `.udd` 在外部被改动；
- 仓库里引用的图片 / 视频源文件被替换；
- 想重新拉一遍嵌入媒体 blob。

### 2.4 syncAll 早退（Plan D）

各视图（outline / document）的 `onInput` 真正写回 `node[field]` 时才把
`this._inputDirty = true`；`syncAll()` 第一行：

```js
if (!this._inputDirty) return;
```

切换视图、自动保存、撤销前等会触发 `syncAll`，但若期间没有任何输入事件，就
省掉一次"扫所有 contentEditable 节点"的成本。Mindmap / Sheet / PPT 没有
contentEditable 输入，`_inputDirty` 永远为 false，`syncAll` 退化为 no-op。

### 2.5 嵌入引用懒加载早退（Plan B）

`_ensureEmbeddedMediaLoaded` 原先每次 `renderCurrentView()` 都做一次：

```js
const dataStr = JSON.stringify(session.data || {});
const needsRefs = dataStr.includes('udd.ref-docs.');
```

改为在打开文件 / 创建会话的那一刻（`_createSessionObj`）算一次并缓存到
`session._needsRefDocsLoad`。后续每次 render 命中标记即 O(1) 早退；
即便后续编辑过程中**新增**了 `udd.ref-docs.` 引用，效果也只是该次嵌入数据
不会被自动加载——这是合理的：嵌入引用的数据来源只能是文件本身的 zip，
新写入的引用键对应的数据本来就不存在于 zip 里，自动加载也是空操作。

### 2.6 异步引用解析早退（Plan C）

`_resolveAsyncRefs` 一开始就先 `viewEl.querySelector('[data-ref-async]')`
确认有目标元素再继续；空文档 / 无跨文档引用的文档直接跳过整个状态机。

## 三、为什么不做"自动版本判定"

考虑过一种更自动化的方案：在 data 上挂一个 `_version` 计数器，每次任何 set 都
`++`。视图缓存附带一个"上次渲染时的 version"，下次进入时比较版本号决定是否重渲。

不采用，理由：

1. **维护成本不可控**。今天能想到要 `++` 的地方覆盖 90%，但每次新加一个数据
   入口（导入 / 同步 / 自动迁移 / 服务端推送 / 协作） 都得记得加一行
   `data._version++`，漏一个就会出现"看起来该刷新但不刷新"的诡异 bug，且
   极难定位。
2. **判定边界模糊**。`undo` 是一次新版本？焦点切换是吗？scrollTop 变化呢？
   一旦开始定义"什么算一次改动"就会被不断追加例外。
3. **本次方案足够覆盖**。所有数据写入路径最终都过 `markDirty` 或显式
   `_invalidateAllViews`，外加一个手动刷新兜底，已经把"应该重渲"和
   "可以省"两类情况干净分开。

## 四、UI 改动

`udd-app.html`：在「渲染 on/off」旁加 `🔄 刷新` 按钮。

```html
<button id="refresh-view"
        onclick="app.refreshCurrentView()"
        title="刷新当前视图（强制重新渲染，引用/媒体重新读取）">🔄 刷新</button>
```

## 六、验证清单

1. 开一个含十几个 t1 节点的大文档，反复在「大纲 / 思维导图 / 文档 / 表格 / 演示」
   tab 间切换，第二次起切回的视图必须**几乎瞬时**（无需 render）；
2. 在大纲里改一个标题 → 切到文档 → 该标题已更新（其它视图被自动失效）；
3. 在大纲里点击节点（仅焦点变化，没敲字）→ 切到文档 → 文档不会重渲一遍；
4. 改一个引用源节点 → 当前视图立即看到新值（contentEditable 即时）；
   切到其它视图也是新值（被自动失效）；
5. 引用的 *外部 .udd 文件* 在外部改动 → 不会自动反映 → 点「🔄 刷新」后看到
   新值（媒体也会重新拉）；
6. 撤销 / 重做 / 撤销后再改 → 三个视图任意切换，都拿到当前 undo 栈对应的版本。
